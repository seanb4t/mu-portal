Each client sends commands to the API and reads one event stream from it. The API is the only way into the server. Inside the server, a game session holds one telnet connection, and the journal records each event.

## How a game session reads telnet

A game session gives the bytes of each read to a framer. The telnet framer passes them to the telnet parser, which does no I/O. The parser reads the telnet commands, answers the option requests of the game and unpacks MCCP2 compression. The framer then gives the session lines, prompts, replies to send, the answers to marks, GMCP messages and protocol errors. A prompt is text with no line end at the end of a read, or text before GA or EOR. The framer reads the text of a world in UTF-8 or ISO-8859-1. The [telnet engine decision](/decisions/telnet-engine/) explains the choice of this design.

## The configuration store

The configuration store is the part of the server that owns the configuration directory. The guide [The configuration files](/guides/configuration/) tells where that directory is. At the start, the store reads the directory once into a snapshot. A snapshot is a copy of the path and the bytes of each file. The store resolves the worlds, checks `server.toml` and checks each client layer from that snapshot. A client layer is one file under `clients/` that sets the keys, the echo line, the layout, the tab label and the statusline of a client. The guide [The client configuration](/guides/client/) describes the layers.

A bad world or a bad `server.toml` stops the start. A bad client layer does not stop the start. The store skips the whole layer and writes one line to stderr that names the file and the reason.

The API has these calls for the configuration:

| Call | What it does |
|---|---|
| `GetClientConfig` | Takes a kind, an OS and a device name. It returns the merged keys and echo, the layout in use, the layout of each world entry, the tab label and the statusline, the revision, the layer that set each field, and a notice for each bad layer of that client |
| `WatchConfig` | A stream. It sends the store hash first. After each reload that changes `clients/`, it sends the new store hash |
| `ReloadConfig` | Reads the directory again. It applies the client layers, and lists the bad files and the changed files that apply only at the restart |
| `ListLayouts` | Returns each layout with its lines: the built-in ones and the good layout files |
| `DescribeLayout` | Takes a layout name, a width and a height. It returns the rectangle and the data source of each block |
| `SaveLayout` | Writes a layout file. With a device name, the layer of that device then names the layout. With a key too, the entry of that world or game names it |
| `EditLayout` | Applies one change to a layout, and saves the result |
| `UseLayout` | Sets the layout of a device, or the layout of one world or one game on that device |

The revision is a hash of the layer files of one client. Only a change to a layer of that client changes it. So the revision stays the same across a restart of the server. The store hash is a hash of every file under `clients/`. The server keeps no state about a client. Each client compares the store hash with the hash of its configuration. If the two differ, the client calls `GetClientConfig`.

## The start of a client

Before the screen opens, `mu client` lists the worlds, opens `WatchConfig`, waits for the first store hash and calls `GetClientConfig`. The three steps share one wait, the `connect_wait` option of the server URL. The client builds its keymap, its echo setting, its layouts, its tab label and its statusline from the reply, and shows a notice for each bad layer.

## A reload

`mu config reload` asks the server to read its directory again. The store applies the new client layers and sends a new store hash on `WatchConfig`. Each attached client then calls `GetClientConfig`. If the revision is new, the client replaces its keymap, its echo setting, its layouts, its tab label and its statusline without a restart. A change to a world or to `server.toml` applies only at the restart of the server.

## A save of the layout

A client changes its layout with a command, with the mouse or in arrange mode. The screen shows the change at once. The client then calls `SaveLayout`, `EditLayout` or `UseLayout`. The store checks the plan with the same rules as the client, writes the file as a whole, and reads the directory again. Each attached client then gets the saved layout, as after a reload. An agent or a script makes the same calls through `mu layout`.
